# TrafoDNA V3.2 preregistered projected-PUF protocol

**Protocol version:** `3.2.0-preregistered`  
**Freeze date:** 31 August 2026  
**Status at freeze:** development may be generated; final scenarios are
defined but unopened.

## Question

V3 produced a stable 26-bit raw response but missed its preregistered
32-bit target. V3.1 proved that no selector could recover 32 mutually
admissible bits from the unchanged unary/pairwise representation. The V3.2
development diagnostic then showed that many eligible candidates repeated
the same small set of population partitions. An enrollment-only projected
representation reached 64 admissible bits on the already observed 20-core
development data.

V3.2 asks a new and narrower question:

> Does the frozen projected challenge-response representation retain at
> least 32 stable, balanced, and mutually admissible bits on a new 64-core
> virtual population and previously ungenerated final scenarios?

V3.2 is not a continuation of the V3 final test. It uses a new virtual
population, a new seed, and a new final holdout.

The first 20 core IDs do not reuse V3 cores because the population seed is
different. All active acquisition noise is keyed by the stable condition ID,
not by the condition's position in a generated subset. This prevents the
separately generated final stage from reusing development noise streams.

## Frozen scenario construction

All 18 scenario rows are generated mechanically from Halton indices 41–58
with bases `[2 3 5 7 11 13]`. The normalized coordinates map to the same
temperature, noise, sensor-gain, reset, stress, and ageing ranges used by V3.

| Role | Condition IDs | Generated by |
|---|---|---|
| Known fitting and validation | 201–208 | `main_v32_prepare` |
| Unseen development | 209–214 | `main_v32_prepare` |
| Locked final holdout | 215–218 | `main_v32_final` only |

The preparation stage must report both `finalRowsGenerated = 0` and
`finalRowsUsed = 0`. It stores neither final features nor final responses.

## Frozen projected-bit construction

The PUF stability transform remains separate from the identity classifier.
It is fitted only on enrollment rows. The projection subspace and thresholds
use enrollment rows; validation repetitions apply the unchanged V3
reliability, worst-condition, aliasing, and correlation screens.

| Parameter | Frozen value |
|---|---:|
| Random projections | 8192 |
| Stable subspace dimensions | 19 |
| Within-variance regularization | 0.25 |
| Energy weighting exponent | 0.50 |
| Projection seed | 20260831 |
| Required bits | 32 |
| Maximum retained bits | 64 |
| Maximum absolute reference correlation | 0.80 |

Exact and complementary enrollment reference patterns are collapsed before
selection. Ineligible fallback bits and error correction remain disabled.

## Development-readiness rule

`main_v32_prepare` evaluates the frozen model using known-test and unseen
development rows only. Final generation remains disabled unless all ten
readiness checks pass. Readiness is not a scientific final result; it is the
predeclared condition for spending the one final holdout.

For readiness, identity metrics use the six unseen-development scenarios.
PUF single-read, worst-scenario, and three-sweep metrics pool known-test and
unseen-development rows. The same numerical thresholds as the final table
below are applied.

## Final acceptance rule

After a passing preparation bundle has been reviewed and archived,
`main_v32_final` may be called once with the literal confirmation token
stored in `defaultV32Config`. It verifies the complete result-relevant
protocol contract, writes `V32_FINAL_OPENED.lock`, and only then generates
conditions 215–218. A failed or interrupted opening remains an observed
opening and must not be silently rerun.

| Final criterion | Requirement |
|---|---:|
| Single-sweep identity accuracy | ≥ 0.60 |
| Single-sweep identity EER | ≤ 0.20 |
| Raw projected-PUF reliability | ≥ 0.90 |
| Projected-PUF uniqueness | 0.45–0.55 |
| Strictly eligible projected bits | ≥ 32 |
| Worst-final-scenario PUF reliability | ≥ 0.85 |
| Three-sweep identity accuracy | ≥ 0.70 |
| Three-sweep identity EER | ≤ 0.15 |
| Three-sweep PUF reliability | ≥ 0.93 |
| Maximum selected-bit reference correlation | ≤ 0.80 |

The V3 passive-gain gate is not reused. Its locked value came from a
different 20-core population and is not a valid baseline for the new 64-core
experiment. The tenth V3.2 gate instead verifies the representation's frozen
mutual-admissibility contract.

The hypothesis is **SUPPORTED** only if all ten final gates pass on the first
opening. Any other result is **NOT SUPPORTED**. Thresholds, bit count,
population, projections, scenarios, or decision logic must not be changed
after inspecting final rows.

## Commands and stopping rule

Preparation only:

```matlab
addpath(genpath(pwd));
run_tests
preparedV32 = main_v32_prepare();
```

Stop after this command, archive the entire `results_v32_preregistered`
directory, and review the printed checks. Do not run the final function as
part of preparation. The final command is deliberately documented in the
source function rather than presented as the next routine step.

## Scientific boundary

This protocol tests numerical behavior inside the existing virtual
pinning-site simulator. It provides no physical transformer measurement,
manufacturing validation, attack analysis, key-derivation analysis, or
cryptographic security proof. A supported V3.2 outcome would justify a
physical measurement study; it would not validate a deployable PUF.

The local contract comparison and lock marker are procedural safeguards, not
an external timestamp or tamper-proof preregistration service. For a formal
claim, archive the source package and its SHA-256 hash or commit it to an
immutable, time-stamped repository before opening the final holdout.
